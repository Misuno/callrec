# callrec — TUI-приложение для записи звонков

Техническое задание и инструкция по реализации. Документ рассчитан на то, чтобы по нему можно было собрать приложение целиком (самостоятельно или с помощью ИИ-ассистента).

## 1. Цель

Записывать звонки из любого приложения (Google Meet в браузере, Telegram, Slack, Zoom) в один аудиофайл с двумя раздельными каналами:

- **левый канал** — микрофон пользователя (вход, выбранный в системе по умолчанию);
- **правый канал** — всё, что звучит в наушниках, то есть собеседники (монитор выхода, выбранного в системе по умолчанию).

Приложение **всегда слушает текущие системные устройства по умолчанию**. Если пользователь отключил внешний микрофон, подключил наушники или Bluetooth-гарнитура сменила профиль, запись автоматически продолжается с новых устройств, без действий пользователя и без остановки записи.

Раздельные каналы нужны для последующей транскрипции: речь пользователя размечается без ошибок, а разметка голосов (диаризация) применяется только к каналу собеседников. Транскрипция в рамки этого приложения не входит, но формат файла должен быть пригоден для неё без конвертации.

## 2. Готовые альтернативы (проверены до принятия решения)

- **OBS Studio** (уже установлен через `programs.obs-studio.enable`). Умеет писать микрофон и звук рабочего стола в разные аудиодорожки, есть кнопки «Запись», «Пауза», «Стоп». Минусы: тяжёлый GUI, всегда пишет видео, дорожки потом нужно извлекать через `ffmpeg`. Годится как запасной вариант.
- **Audacity, GNOME Sound Recorder, Kooha** — пишут только один источник за раз.
- **Виртуальный стерео-источник PipeWire** (null-sink + `pw-link` микрофона в FL и монитора в FR) позволяет писать любым рекордером, который умеет только один источник. Минус: связи статические и не следуют за сменой устройства.
- **DAW (Ardour, Reaper)** — умеют всё, но избыточны.

Готового лёгкого приложения с ровно этим поведением не найдено, поэтому пишем своё.

## 3. Интерфейс

Один экран. Управление клавишами и мышью (кнопки кликабельны).

```
┌─ callrec ────────────────────────────────────────────────────────┐
│                                                                  │
│  Микрофон (L)    Jabra Evolve2 65 Mono                           │
│                  bluez_input.70_BF_92_00_00_00.0                  │
│                  ▕██████████▁▁▁▁▁▁▁▁▁▁▏ -18 dB                     │
│                                                                  │
│  Собеседники (R) Jabra Evolve2 65 (монитор)                      │
│                  bluez_output.70_BF_92_00_00_00.1                 │
│                  ▕████▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▏ -31 dB                     │
│                                                                  │
│  ● ЗАПИСЬ   00:23:41   ~/Calls/2026-10-21_14-00.flac             │
│                                                                  │
│  14:23:05  Микрофон: Встроенный микрофон → Jabra Evolve2 65 Mono  │
│                                                                  │
│  [r] Запись   [p] Пауза   [s] Стоп   [q] Выход                    │
└──────────────────────────────────────────────────────────────────┘
```

### Элементы

1. **Два блока устройств** — человекочитаемое описание (`node.description`) и системное имя (`node.name`) устройства, к которому сейчас подключён соответствующий поток записи. Обновляются автоматически.
2. **Индикатор уровня** для каждого канала. Работает всегда, когда приложение открыто: и до записи (чтобы убедиться, что микрофон и звук работают), и во время неё, и на паузе.
3. **Статус**: `ОЖИДАНИЕ`, `● ЗАПИСЬ`, `❚❚ ПАУЗА`, `СОХРАНЕНИЕ…`. Таймер показывает чистую длительность записи без пауз. Путь к итоговому файлу.
4. **Журнал событий** — последние 3 события со временем: смена устройств, ошибки, предупреждения (см. раздел 6).
5. **Кнопки**:

| Клавиша | Действие | Доступно в состоянии |
| --- | --- | --- |
| `r` | Начать запись | ОЖИДАНИЕ |
| `p` | Пауза / продолжить | ЗАПИСЬ, ПАУЗА |
| `s` | Остановить и сохранить | ЗАПИСЬ, ПАУЗА |
| `q` | Выход (во время записи — с подтверждением, запись сохраняется) | любое |

Недоступные кнопки отображаются приглушёнными.

## 4. Технический стек

Язык — **Rust** (stable).

| Задача | Crate / инструмент |
| --- | --- |
| TUI | `ratatui` + `crossterm` (с включённой поддержкой мыши) |
| Захват звука | `pipewire` (официальные Rust-биндинги к libpipewire) |
| Обмен данными между потоками | `crossbeam-channel` или `std::sync::mpsc` |
| Метаданные | `serde`, `serde_json` |
| Время | `chrono` (локальное время с часовым поясом для имён файлов и JSON) |
| Ошибки | `anyhow` |
| Кодирование FLAC | внешняя утилита `flac` (пакет `flac`), PCM подаётся в stdin |

Почему нативный PipeWire, а не ffmpeg: ffmpeg привязывается к конкретному имени устройства при старте и не умеет следовать за сменой устройства по умолчанию. Поток PipeWire без явной цели (`target.object`) WirePlumber сам подключает к устройству по умолчанию и **сам переподключает** при его смене. Это и есть требуемое поведение, без перезапуска записи.

Почему внешний `flac`: потоковое кодирование с корректным заголовком в конце, проверенная реализация. Файл, оборванный аварийным завершением, остаётся декодируемым до последнего записанного кадра.

Системные требования: PipeWire с WirePlumber (в NixOS включены через `services.pipewire.enable`).

## 5. Архитектура

### 5.1. Потоки выполнения

```
┌──────────────────────┐   PCM-блоки + события    ┌───────────────────┐
│ PipeWire-поток       │ ───────────────────────▶ │ Поток записи      │
│ (pipewire MainLoop)  │                          │ (микшер L/R,      │
│ • поток «mic»        │                          │  уровни, flac)    │
│ • поток «them»       │                          └─────────┬─────────┘
│ • registry/metadata  │                                    │ уровни, состояние
└──────────▲───────────┘                                    ▼
           │ команды (стоп)                       ┌───────────────────┐
           └───────────────────────────────────── │ UI-поток (ratatui)│
                                                  └───────────────────┘
```

- **PipeWire-поток.** Объекты `pipewire` не являются `Send`, поэтому весь PipeWire живёт в одном выделенном потоке со своим `MainLoop`. Команды из других потоков доставляются через `pipewire::channel`.
- **Поток записи.** Получает PCM от обоих потоков захвата, выравнивает их во времени, считает уровни, при активной записи пишет стерео-PCM в stdin процесса `flac`.
- **UI-поток.** Отрисовка раз в 50 мс, обработка клавиш и мыши. Состояние получает из канала, команды отправляет в потоки.

### 5.2. Захват: два потока PipeWire

Создаются два потока захвата (`pipewire::stream::Stream`), оба с запрошенным форматом **S16LE, 1 канал, 16000 Гц**. Адаптер PipeWire сам выполнит ресемплинг и сведение в моно, каким бы ни было устройство.

**Поток «mic»** — микрофон:

```
media.type     = Audio
media.category = Capture
media.role     = Communication
node.name      = callrec-mic
```

**Поток «them»** — монитор выхода:

```
media.type          = Audio
media.category      = Capture
media.role          = Communication
node.name           = callrec-them
stream.capture.sink = true
```

`stream.capture.sink = true` говорит WirePlumber подключить поток к монитору устройства вывода по умолчанию, а не к входу.

Обязательные условия:

- **не задавать `target.object`** — иначе поток будет привязан к конкретному устройству и не будет следовать за сменой;
- **не задавать `node.dont-reconnect`**;
- флаги подключения: `AUTOCONNECT | MAP_BUFFERS | RT_PROCESS`.

Колбэк `process` копирует сэмплы из буфера в канал потока записи вместе с меткой времени получения (`Instant::now()`). Никаких аллокаций и блокировок в колбэке: использовать заранее выделенный кольцевой буфер или `try_send` с отбрасыванием при переполнении.

Ссылка на проверку поведения: `pw-record -P '{ stream.capture.sink = true }' test.wav` пишет монитор устройства по умолчанию и переключается при его смене. Приложение воспроизводит то же поведение.

### 5.3. Отслеживание устройств по умолчанию

В PipeWire-потоке подписаться на registry:

1. Найти объект `Metadata` с именем `default`. Слушать ключи `default.audio.source` и `default.audio.sink`. Значение — JSON вида `{"name":"bluez_input.70_BF_92_00_00_00.0"}`.
2. Для узлов (`Node`) хранить соответствие `node.name → node.description`, чтобы показывать понятные названия.
3. Слушать связи (`Link`), у которых входной узел — `callrec-mic` или `callrec-them`. Узел на другом конце — устройство, с которого реально идёт запись. Именно его показывать в UI.

При смене устройства по умолчанию записать событие в журнал UI и в метаданные: `14:23:05 Микрофон: Встроенный микрофон → Jabra Evolve2 65 Mono`.

**Страховка.** Если устройство по умолчанию сменилось, а поток через 2 секунды всё ещё подключён к старому устройству (или ни к чему не подключён), приложение само переподключает поток: `disconnect()` и повторный `connect()` без цели. Событие пометить в журнале как «переподключено вручную». В нормальной работе WirePlumber делает это сам, и страховка не срабатывает.

### 5.4. Выравнивание каналов и тишина при переключении

Устройства могут иметь разные аппаратные часы, а при переключении устройства поток несколько сотен миллисекунд не получает данных. Чтобы каналы не разъезжались, поток записи работает **от собственных часов**:

Задержка канала — это число сэмплов в его очереди. Каналы синхронны, пока задержки обоих каналов одинаковы. Поэтому микшер держит в каждой очереди один и тот же целевой уровень и выравнивает его отдельно для каждого канала.

1. Для каждого канала — очередь сэмплов (`VecDeque<i16>`).
2. Каждые 100 мс (по `Instant`, без накопления ошибки) поток записи берёт ровно 1600 сэмплов (блок) из каждой очереди. Если поток записи опоздал на несколько тактов, пропущенные такты выполняются подряд, чтобы время в файле не отставало от реального.
3. **Запас.** Целевой уровень очереди перед взятием блока — 3200 сэмплов: блок плюс запас 1600 сэмплов (100 мс). Запас поглощает неравномерность поступления данных (порции PipeWire, Bluetooth). Канал начинает выдавать данные только после того, как очередь набрала целевой уровень; до этого он выдаёт тишину и не расходует очередь (заполнение).
4. **Нехватка.** Если в момент такта в очереди меньше 1600 сэмплов, канал выдаёт всё, что есть, остаток блока дополняется нулями, и канал снова переходит в заполнение (п. 3). Так переключение устройства даёт короткую тишину в одном канале, а не сдвиг одного канала относительно другого.
5. **Переполнение.** Если в момент такта в очереди больше 4800 сэмплов (300 мс), самые старые сэмплы отбрасываются до целевого уровня 3200. Это компенсирует всплески данных после переключения устройства.
6. **Дрейф часов.** Часы устройств и системные часы немного расходятся (десятки ppm, за час — до сотен миллисекунд). Микшер запоминает уровень очереди на каждом такте. Каждые 2 секунды (20 тактов): если минимальный уровень за окно выше целевого больше чем на 320 сэмплов (20 мс), разница отбрасывается с начала очереди; если максимальный уровень ниже целевого больше чем на 320 сэмплов, в начало очереди добавляется столько же нулей. Так задержка каждого канала остаётся в пределах ±20 мс от целевой, и рассинхрон каналов не накапливается (критерий 9.10).
7. Микшер работает непрерывно с запуска приложения: уровни нужны всегда (раздел 5.5). Старт и продолжение записи начинаются со следующего блока; очищать очереди не нужно, синхронность поддерживается постоянно.
8. Блоки каналов перемежаются в стерео (L = mic, R = them) и пишутся в stdin `flac`.

Пороги и интервалы (1600, 3200, 4800, 100 мс, 2 с, 320) вынести в константы.

### 5.5. Уровни

Для каждого 100-мс блока каждого канала считать RMS и переводить в dBFS: `20 · log10(rms / 32768)`, нижний предел −90 dB. Уровни считаются всегда, независимо от того, идёт ли запись. Индикатор в UI — с плавным спадом (peak hold ~1 с).

### 5.6. Запись, пауза, стоп

- **Старт** (`r`): создать каталог `~/Calls`, запустить процесс

  ```bash
  flac --silent --force-raw-format --endian=little --sign=signed \
       --channels=2 --bps=16 --sample-rate=16000 \
       -o "$HOME/Calls/2026-10-21_14-00.flac.part" -
  ```

  и начать писать блоки в его stdin.
- **Пауза** (`p`): перестать писать блоки в stdin. Потоки захвата и индикаторы продолжают работать. Процесс `flac` остаётся запущенным.
- **Продолжить** (`p`): снова писать блоки со следующего такта (п. 5.4.7). В файле пауза просто отсутствует.
- **Стоп** (`s`): закрыть stdin `flac`, дождаться завершения процесса (код возврата 0), переименовать `.flac.part` → `.flac`, записать JSON с метаданными.

Сегменты и склейка не нужны: запись — один непрерывный поток PCM.

### 5.7. Итоговые файлы

```
~/Calls/2026-10-21_14-00.flac   # стерео FLAC, 16 кГц, 16 бит; L = я, R = собеседники
~/Calls/2026-10-21_14-00.json   # метаданные
```

Имя — время старта записи. Если файл уже существует, добавлять суффикс `-2`, `-3`. Час записи занимает порядка 50–100 МБ.

Метаданные:

```json
{
  "started_at": "2026-10-21T14:00:12+02:00",
  "finished_at": "2026-10-21T14:47:03+02:00",
  "duration_sec": 2701.4,
  "channels": { "0": "me", "1": "them" },
  "pauses": [
    { "at_sec": 1210.0, "duration_sec": 95.2 }
  ],
  "device_changes": [
    { "at_sec": 0.0,    "channel": "me",   "device": "alsa_input.pci-0000_00_1f.3.analog-stereo", "description": "Встроенный микрофон" },
    { "at_sec": 0.0,    "channel": "them", "device": "alsa_output.pci-0000_00_1f.3.analog-stereo", "description": "Встроенные динамики" },
    { "at_sec": 1383.5, "channel": "me",   "device": "bluez_input.70_BF_92_00_00_00.0", "description": "Jabra Evolve2 65 Mono" }
  ]
}
```

`at_sec` — позиция в итоговом файле (без учёта пауз). По `device_changes` при разборе записи видно, где мог быть короткий провал звука.

## 6. Надёжность

Главный риск — потерять запись важного звонка. Поэтому:

1. **Смена устройства** — автоматически (раздел 5.3), запись не прерывается.
2. **Устройства нет вообще** (например, отключили единственный микрофон): канал пишет тишину, индикатор и блок устройства подсвечиваются красным с текстом «нет устройства». Как только устройство появится, поток подключится к нему сам.
3. **Тишина в канале**: если уровень канала ниже −60 dB дольше 60 секунд во время записи — подсветить блок этого канала жёлтым. Для правого канала это нормально, когда собеседники молчат, поэтому только подсветка, без звуков и диалогов.
4. **Падение процесса `flac`** (неожиданный выход, ошибка записи в pipe): переименовать текущий `.flac.part` в `<имя>-part1.flac`, запустить новый процесс `flac` в `<имя>-part2.flac.part`, сообщить в журнале. Запись продолжается.
5. **Потеря соединения с PipeWire** (перезапуск `pipewire.service`): пересоздать контекст и потоки с паузой 1 секунда между попытками. Пока соединения нет, оба канала пишут тишину, чтобы не сбивать время в файле.
6. **Аварийное завершение приложения**: при запуске искать `~/Calls/*.flac.part`. Если есть — предложить: `[y]` восстановить (`flac -d` с `--decode-through-errors`, затем повторное кодирование в `.flac`), `[d]` удалить, `[l]` оставить на потом.
7. **Выход во время записи**: `q` спрашивает подтверждение, после чего запись останавливается и сохраняется как при `s`. `Ctrl+C` и `SIGTERM` ведут себя так же, без подтверждения. Терминал восстанавливается в любом случае, включая панику (`std::panic::set_hook` + восстановление `crossterm`).
8. **Мало места на диске**: перед стартом проверить, что в `~/Calls` свободно хотя бы 1 ГБ; иначе предупреждение.

## 7. Структура проекта

```
callrec/
├── Cargo.toml
├── Cargo.lock
├── default.nix          # Nix-пакет (раздел 8)
└── src/
    ├── main.rs          # запуск потоков, обработка сигналов, восстановление терминала
    ├── pw.rs            # PipeWire: MainLoop, потоки захвата, registry, metadata
    ├── mixer.rs         # очереди, выравнивание по времени, уровни
    ├── writer.rs        # процесс flac, .part-файлы, метаданные, восстановление
    ├── app.rs           # состояние приложения (конечный автомат), обработка команд
    └── ui.rs            # отрисовка ratatui, клавиши, мышь
```

Состояние приложения — конечный автомат: `Idle → Recording ⇄ Paused → Saving → Idle`.

Модули `mixer` и `writer` не зависят от PipeWire и тестируются юнит-тестами:

- выравнивание: недостача данных в одном канале дополняется тишиной, а не сдвигает каналы;
- отбрасывание при переполнении очереди;
- коррекция дрейфа часов удерживает задержку канала около целевой;
- расчёт `at_sec` с учётом пауз;
- восстановление `.flac.part`.

### 7.1. Порядок реализации

От простого и проверяемого тестами к рискованному. Каждый этап — отдельный коммит. Этап завершён, когда проходят `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` и `cargo test`.

1. **`mixer.rs`** — без PipeWire. Очереди каналов, такт 100 мс, запас и заполнение, дополнение тишиной, отбрасывание при переполнении, коррекция дрейфа (раздел 5.4), RMS → dBFS (раздел 5.5). Пороги — константы. Юнит-тесты: выравнивание, заполнение, переполнение, дрейф, такт, уровни.
2. **`writer.rs`** — без PipeWire. Процесс `flac`, `.flac.part` → `.flac`, суффиксы `-2`, `-3`, JSON-метаданные, расчёт `at_sec` с учётом пауз (раздел 5.7). Перезапуск при падении `flac` (раздел 6.4), восстановление `.flac.part` (раздел 6.6), проверка свободного места (раздел 6.8). Тесты на реальном `flac` из dev shell во временном каталоге.
3. **`pw.rs`** — PipeWire-поток: `MainLoop`, два потока захвата (раздел 5.2), registry, metadata `default`, связи (раздел 5.3), страховочное переподключение, пересоздание контекста при потере соединения (раздел 6.5). Проверка: временный консольный режим, который печатает устройства и уровни; смена устройства по умолчанию в KDE отражается в выводе.
4. **`app.rs`** — конечный автомат `Idle → Recording ⇄ Paused → Saving → Idle`, команды, журнал событий, таймер без пауз, подсветка «нет устройства» и тишины (разделы 6.2, 6.3). Тесты переходов состояний без UI.
5. **`ui.rs`** — экран из раздела 3, клавиши, мышь, приглушённые недоступные кнопки, индикаторы с peak hold.
6. **`main.rs`** — запуск потоков, `Ctrl+C` и `SIGTERM`, panic hook с восстановлением терминала, подтверждение выхода во время записи, диалог восстановления `.flac.part` при запуске (раздел 6.7).
7. **`default.nix`** — Nix-пакет (раздел 8), подключение в home-manager.
8. **Приёмка** — пройти все пункты раздела 9 в наушниках.

## 8. Сборка в NixOS

Разместить проект в репозитории конфигурации, например `~/nixos/pkgs/callrec/`.

```nix
# pkgs/callrec/default.nix
{ lib, rustPlatform, pkg-config, pipewire, flac, makeWrapper }:

rustPlatform.buildRustPackage {
  pname = "callrec";
  version = "0.1.0";
  src = ./.;
  cargoLock.lockFile = ./Cargo.lock;

  nativeBuildInputs = [
    pkg-config
    rustPlatform.bindgenHook   # crate pipewire генерирует биндинги через bindgen
    makeWrapper
  ];
  buildInputs = [ pipewire ];

  postInstall = ''
    wrapProgram $out/bin/callrec --prefix PATH : ${lib.makeBinPath [ flac ]}
  '';

  meta.mainProgram = "callrec";
}
```

Подключение в home-manager (например, в `users/misuno/apps/communication.nix`):

```nix
home.packages = [ (pkgs.callPackage ../../../pkgs/callrec { }) ];
```

Файлы проекта (включая `Cargo.lock`) должны быть добавлены в git (`git add`), иначе flake их не увидит.

Среда разработки без пересборки системы:

```bash
nix shell nixpkgs#cargo nixpkgs#rustc nixpkgs#pkg-config nixpkgs#pipewire.dev \
  nixpkgs#clang nixpkgs#flac
export LIBCLANG_PATH="$(nix eval --raw nixpkgs#libclang.lib)/lib"
cargo run
```

## 9. Критерии приёмки

Проверять в наушниках.

1. При запуске отображаются текущие микрофон и устройство вывода по умолчанию; индикаторы реагируют на голос и на видео в браузере.
2. **Автоматическое переключение без записи**: смена устройства по умолчанию в настройках KDE отражается в интерфейсе и в индикаторах в течение 2 секунд.
3. **Автоматическое переключение во время записи**: запись → отключить USB-микрофон → подключить обратно → переключить вывод на наушники → стоп. Запись не прерывалась; в файле звук есть со всех устройств; в JSON перечислены все переключения; провалы звука не длиннее 1 секунды.
4. Запись 1 минута → пауза 30 секунд → запись 1 минута → стоп. Итоговый файл длится ~2 минуты, `ffprobe` показывает `2 channels` и `16000 Hz`.
5. Каналы раздельны:
   ```bash
   ffplay -nodisp -af "pan=mono|c0=c0" файл.flac   # только пользователь
   ffplay -nodisp -af "pan=mono|c0=c1" файл.flac   # только собеседники
   ```
6. Тестовый звонок в Google Meet и в Telegram с Bluetooth-гарнитурой: когда приложение звонка включает микрофон и гарнитура переходит из A2DP в HFP, запись продолжается с нового профиля автоматически.
7. Отключить единственный микрофон во время записи: блок подсвечивается красным, запись продолжается; после подключения микрофон подхватывается сам.
8. `systemctl --user restart pipewire wireplumber` во время записи: запись продолжается после восстановления соединения, в файле на месте перезапуска — тишина, без сдвига каналов.
9. `kill -9` процесса во время записи → повторный запуск предлагает восстановить `.flac.part`, восстановленный файл воспроизводится.
10. Запись длительностью 1 час: рассинхрон каналов в конце — не больше 100 мс (проверить по хлопку в ладоши рядом с микрофоном при включённом звуке из колонок или по моменту, когда звук собеседника попал и в микрофон).

## 10. Вне рамок первой версии

- Транскрипция и итоги звонка (отдельный инструмент, работает с готовым FLAC).
- Ручной выбор устройств вместо системных по умолчанию.
- Автостарт записи при появлении звонка.
- Значок в системном трее.
